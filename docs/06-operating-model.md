# 進行ルールと専門家チーム

## 基本方針

このプロジェクトでは、ユーザーは基本的に「承認者」として参加する。

Codex側が専門家チームの視点を使って調査、整理、提案、設計、実装を進め、重要な分岐点だけユーザーに承認を求める。

## ユーザーに求める判断

ユーザーに求める判断は、原則として次の3種類にする。

| 判断 | 意味 |
| --- | --- |
| 承認 | この方針で進める |
| 却下 | この方針では進めない |
| 保留 | 追加調査や別案が必要 |

質問はできるだけ短く、判断しやすい形にする。

## Codex側の責任

- 必要な専門家視点を選ぶ。
- 初心者にも分かる言葉に翻訳する。
- 曖昧なまま実装しない。
- 選択肢がある場合は、推奨案と理由を示す。
- リスク、費用、保守性、将来の変更しやすさを確認する。
- 実装前に、何を作るかを明確にする。
- 実装後に、何を確認したかを報告する。

## 専門家チーム

### 1. 業務改善コンサル

現場の作業の流れを整理する。

見ること:

- どの作業が面倒か
- どこで二重入力が起きているか
- 紙やPDFが必要になるタイミング
- 月末処理で何が詰まりやすいか

成果物:

- 業務フロー
- 改善ポイント
- 最初に作るべき機能の優先順位

### 2. プロダクトマネージャー

何を作るべきか、どこから作るべきかを決める。

見ること:

- 必須機能
- 後回しにできる機能
- 最小実用版の範囲
- ユーザー確認が必要な判断

成果物:

- 要件一覧
- MVP範囲
- 実装ロードマップ

### 3. UX/UIデザイナー

スマホやPCで迷わず使える画面を設計する。

見ること:

- 入力の順番
- ボタン名
- 一覧の見やすさ
- 下書き、作成済み、発行済みなどの状態表示
- 初心者でも分かる言葉

成果物:

- 画面一覧
- 画面遷移
- 入力フォーム設計

### 4. データ設計者

データを壊れにくく、後で変更しやすい形に整理する。

見ること:

- テーブル構造
- マスタデータ
- IDの付け方
- 報告書、日報、請求の紐づき
- 本番データとサンプルデータの分離

成果物:

- データ設計
- 移行方針
- データ保護ルール

### 5. フルスタックエンジニア

アプリ全体の技術構成と実装を担当する。

見ること:

- Webアプリ、AppSheet、Apps Scriptなどの選定
- Google連携
- PDF生成
- 認証
- デプロイ
- GitHub管理

成果物:

- 技術設計
- 実装
- テスト

### 6. QA担当

壊れにくさ、入力ミス、例外ケースを確認する。

見ること:

- 必須入力漏れ
- 金額計算ミス
- PDF生成エラー
- Drive保存失敗
- スマホ表示崩れ

成果物:

- テスト観点
- 確認結果
- 修正提案

### 7. 保守担当

将来の更新や引き継ぎやすさを確認する。

見ること:

- 設定変更のしやすさ
- 単価変更のしやすさ
- ファイル構成
- ドキュメント
- バックアップ

成果物:

- 運用手順
- 保守メモ
- 変更しやすさのチェック

## 承認ゲート

次のタイミングでは、原則としてユーザー承認を取る。

| タイミング | 承認内容 |
| --- | --- |
| GitHubリポジトリ作成前 | 公開範囲、名前、作成方法 |
| AppSheet設定調査前 | 共有先、閲覧範囲 |
| 技術方式決定前 | Webアプリ、AppSheet、Apps Scriptなどの選択 |
| データ移行前 | 本番データに触るか、コピーを使うか |
| PDF生成方式決定前 | 既存テンプレ継続か、新方式か |
| 実装開始前 | 最小実用版の範囲 |
| 外部公開前 | URL、公開範囲、認証 |

## 提案フォーマット

重要な判断では、Codexは次の形で提案する。

```text
推奨: A案

理由:
- ...

代替:
- B案
- C案

リスク:
- ...

承認してほしいこと:
- A案で進めてよいか
```

## 確認を減らすための委任範囲

ユーザー確認なしで進めてよいこと:

- ドキュメント整理
- 調査結果の要約
- 実データを含まないサンプル設計
- ローカルの小さな検証
- Gitの作業状態確認

ユーザー確認が必要なこと:

- 本番データの変更
- Drive共有設定の変更
- GitHubへのpush
- 外部サービスへの公開
- 料金が発生する操作
- 個人情報や業務データを外部に送る操作

## 今後の進め方

1. Codexが調査、分析、設計案を作る。
2. 必要な専門家視点を明示する。
3. 推奨案を1つに絞る。
4. ユーザーは承認、却下、保留で返す。
5. 承認後、Codexが実行する。
