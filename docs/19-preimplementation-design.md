# オシゴトアプリ 実装前設計

Status: Design baseline, implementation not started
Date: 2026-07-23

## 1. 目的

オシゴトアプリは、既存AppSheetから業務上必要な機能とデータを引き継ぎながら、次の点を改善する。

- 現場で迷わず入力できること
- 入力途中の内容を失わないこと
- PDF作成の成功・処理中・失敗が分かること
- 領収書を撮影、加工、確認して帳票へ貼れること
- 帳票の位置や文字設定を、コードを直接書かずに調整できること
- 更新、バックアップ、障害対応、機能追加を安全に行えること

## 2. 対象範囲

初期リリースで対象とする機能:

1. Googleアカウントによるログイン
2. 書類ハブ（完了報告書、丸産報告書）
3. 下書き保存、再編集、完了確定
4. 完了報告書の新書式入力
5. 丸産報告書の新書式入力
6. 領収書の撮影または画像選択、プレビュー、トリミング、回転、白黒化
7. 完了報告書と丸産報告書のPDF作成
8. PDFの保存、閲覧、再作成履歴
9. 管理者向け設定、帳票レイアウト調整、作業者設定

初期リリース後に検討する機能:

- 月報と請求書の正式対応
- OCRによる領収書読み取り
- オフライン入力
- ネイティブスマホアプリ化
- 通知、メール送信、外部サービス連携

## 3. 画面と業務の流れ

### 利用者の流れ

1. ログイン
2. 書類種類を選択
3. 新規作成または下書きを再開
4. 入力画面で必須項目を入力
5. 領収書があれば撮影または選択して加工
6. 入力内容の確認画面でエラーとPDFプレビューを確認
7. 下書き保存または完了確定
8. PDF作成ジョブの状態を確認
9. 完成したPDFを開く

### 重要な状態

`draft` は編集可能、`ready` はPDF作成待ち、`processing` は作成中、`completed` はPDF完成、`failed` は失敗して再試行可能とする。

状態を画面に表示し、処理中に同じPDF作成を重複実行しない。

## 4. 安定性の設計

- 入力内容は自動保存または明示保存で保持する。
- PDF作成は入力画面と分離したジョブとして扱う。
- 同じレコードから同時に複数ジョブを起動しない。
- 失敗時は入力データを残し、原因、再試行ボタン、問い合わせ用IDを表示する。
- PDFを一時ファイルへ作成し、検証成功後に完成フォルダへ移動する。
- 作成途中のPDFを完成品として表示しない。
- 重要な処理には作成者、作成日時、更新日時、バージョンを記録する。
- 元画像と加工画像を分け、加工失敗で元画像を失わない。
- 本番データで試す前に、サンプルデータでPDF作成とエラー処理を検証する。

## 5. 使いやすさの設計

- 入力欄を業務の順番に並べる。
- 項目ごとに「必須」「任意」「自動計算」「入力不要」を表示する。
- 長文欄は複数行入力にする。
- Enterによる改行をPDFへ反映する。
- 枠幅に合わせて自動折り返しする。
- 枠高に収まらない場合は、文字を切らずに該当欄を知らせる。
- 数値欄は数字以外を受け付けず、金額の意味を補助説明する。
- 画面を閉じる前に未保存変更を知らせる。
- スマホでは片手操作、PCでは一覧性を優先する。
- 操作完了後は短い結果表示を出し、現在位置を見失わないようにする。

## 6. PDFとレイアウト調整

PDFは新書式PDFを背景として直接描画する方式を基本とする。既存Googleスライドとタグは、位置と項目対応を確認するための参照資産として残す。

帳票設定を次のように分離する:

- fieldId
- x, y, width, height
- fontFamily, fontSize, minFontSize
- lineHeight, alignment
- required, visible, maxLines
- imageFit, imageRotation

管理者画面では、対象帳票を選び、プレビューを見ながら位置、幅、高さ、文字サイズを変更できるようにする。設定変更は履歴を残し、前の設定へ戻せるようにする。

## 7. データ構造の原則

既存の1表構成をそのまま拡大せず、役割を分ける。初期段階では移行の容易さを優先し、互換列を残す。

- reports: 書類本体、状態、作成者、日時
- report_items: 工事内容、作業内容、作業者などの繰り返し項目
- attachments: 元画像、加工画像、PDF、ファイルID
- pdf_jobs: PDF作成依頼、状態、エラー、再試行回数
- users: 利用者、役割、固定作業者設定
- masters: 材料、交通費、会社情報など
- template_configs: 帳票レイアウト設定とバージョン

## 8. 権限

- 一般利用者: 自分の下書き作成、編集、PDF確認
- 管理者: 全件確認、再作成、ユーザー設定、帳票設定、マスタ更新
- 閲覧者: 完成PDFと必要な一覧のみ閲覧

権限は画面を隠すだけでなく、サーバー側でも確認する。

## 9. GitHubと運用

- `main` は確認済みの版だけを置く。
- 機能ごとにブランチを作る。
- 変更前に設計、変更後にテスト結果を記録する。
- リリースごとにバージョン番号と変更内容を残す。
- 本番データ、画像、認証情報をGitHubへ保存しない。
- 設定変更も履歴化し、誰がいつ変更したか分かるようにする。
- 障害時は直前の安定版へ戻せるようにする。
- 月1回以上、復旧手順とバックアップを確認する。

## 10. 実装前の受け入れ基準

次を満たすまで実装完了とはしない。

- 完了報告書の承認済み項目が全て入力できる。
- 丸産報告書の承認済み項目が全て入力できる。
- 消費税は合計の10%を自動計算し、1円未満を切り捨てる。
- 消費税は手動上書きできる。
- 改行と自動折り返しがPDFで再現される。
- 文字が枠外へはみ出すPDFを保存しない。
- 領収書の元画像を失わず、加工画像を確認できる。
- PDFの貼り付け位置を設定変更できる。
- PDF成功、処理中、失敗、再試行が確認できる。
- 同じ処理を二重実行しても重複PDFを作らない。
- 権限外のデータを編集できない。
- GitHubの履歴から変更理由と復旧版を確認できる。
- サンプルデータで主要操作を一通り再実行できる。
