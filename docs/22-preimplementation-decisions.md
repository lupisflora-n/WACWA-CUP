# オシゴトアプリ 実装前の最終判断案

Status: Awaiting user approval
Date: 2026-07-23

## 判断1: 公開環境

### 推奨

Googleアカウントで利用するWebアプリを基本とし、スマホではPWAとしてホーム画面から使える構成にする。

### 理由

- PCとスマホの両方で使える。
- App StoreやGoogle Playの審査を最初から必要としない。
- GitHubで更新しやすい。
- 将来、必要ならネイティブアプリ化できる。

### 変更可能性

公開前に別方式へ変更できる。初期実装をこの方式にしても、データやPDF処理を分離しておけば移行しやすい。

## 判断2: 本番データの扱い

### 推奨

初期実装はサンプルデータ専用の環境で行い、動作確認後に本番データを新構造へ移行する。旧Sheetsは互換参照用として一定期間残す。

### 理由

- 開発中のミスで本番データを壊さない。
- 旧AppSheetとの比較ができる。
- 問題があれば旧アプリへ戻せる。

### 変更可能性

本番切替時に、旧形式を読み取る互換層を残すか、完全移行するかを選択できる。

## 判断3: 旧AppSheetの保持期間

### 推奨

新アプリの本番稼働後、3か月間は旧AppSheetを参照専用で残す。その後、利用状況と保存要件を確認して停止または長期保管する。

### 理由

- 過去帳票の照合ができる。
- 新アプリで見つかった移行漏れを確認できる。
- すぐに旧環境を消すリスクを避けられる。

### 注意

旧アプリを編集用として並行運用するとデータの二重管理になるため、原則として参照専用にする。

## 判断4: 領収書の枚数

### 推奨

初期版は1報告につき複数枚対応にする。ただし、最初のPDF書式には1枚目を正式貼り付け枠へ出力し、2枚目以降は添付資料として保存する。

### 理由

- 実務上、領収書が複数になる可能性を残せる。
- 1枚用の帳票レイアウトを壊さない。
- 後から2枚目以降の帳票出力を追加しやすい。

### 変更可能性

運用上1枚で十分と分かった場合は、画面を1枚入力に制限できる。

## 承認後の進行

4項目を承認したら、次の順で進める。

1. サンプルデータ専用環境を作る。
2. GitHub上でプロトタイプ用ブランチを作る。
3. ログイン、ホーム、書類選択、下書き保存を作る。
4. 完了報告書と丸産報告書の入力画面を作る。
5. 領収書編集画面を作る。
6. PDF直接描画をサンプル帳票で検証する。
7. テスト結果を記録し、次の承認を受ける。

ここでいう「作る」はサンプル環境だけを対象とし、本番のAppSheet、Sheets、Drive、PDF台紙は変更しない。

## ユーザーに確認する回答形式

次のように回答できる。

`1 OK、2 OK、3 OK、4 OK`

変更したい項目があれば、番号と内容だけを指定する。
