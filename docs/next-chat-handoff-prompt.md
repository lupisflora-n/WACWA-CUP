## 目的

既存のAppSheetアプリを捨てて別物を作るのではなく、現行アプリを新しいアプリへ引っ越すように移行します。最優先は、現行アプリでできることを新アプリでも同じようにできることです。そのうえで、現行AppSheetの制約を超えて、帳票の差し替え、タグ位置調整、保守性、将来の機能追加を実現します。プロジェクト名は「オシゴトアプリ」、GitHubリポジトリは `lupisflora-n/WACWA-CUP` です。

## 必須の移行範囲

1. 現行アプリの画面、フォーム、入力項目、一覧、下書き、完了、履歴、PDF生成、共有、領収書処理、権限、通知、データ保存を棚卸しする。
2. 現行アプリと新アプリの機能対応表を作り、完全一致できた項目と未確認項目を明示する。
3. 現行の「工事完了報告書」と「丸産報告書」の流れを保ったまま、新しい台紙へ差し替える。
4. フォーム入力値を台紙へ描画し、会社提出用の元PDF書式を維持したPDFを作成できるようにする。単なる別デザインの帳票を先に作らない。
5. 既存項目のフォーム名は現行アプリの名称を最優先する。新規項目のフォーム名は新台紙から読み取った項目タイトルを初期値にする。
6. 「項目タイトル」と「タグ文字列」は別物として管理し、どちらも編集できるようにする。タグはワンクリックでコピーできるようにする。
7. 新規台紙に必要なタグを追加でき、タグの配置、位置、幅、高さ、文字サイズなどを設定画面または専用の調整画面で変更できるようにする。できればドラッグ操作と数値入力の両方を用意する。
8. 台紙のプレビューに実際の新PDFを背景として表示し、タグとサンプル入力値の描画結果をその場で確認できるようにする。
9. 調整値はコードに埋め込まず、テンプレート設定・項目定義・タグ定義・配置定義を分離して保存する。台紙のバージョンを持たせ、変更履歴と初期状態への復元を可能にする。
10. 現行アプリにある領収書添付、撮影、トリミング、白黒加工・視認性向上、貼り付け位置、帳票への出力を確認し、移行対象に含める。未実装なら「現行との違い」として扱う。

## 確定している帳票ルール

- 工事内容は複数行入力。ユーザーが入力した改行をPDFにも反映し、枠内で自動折り返しする。
- 数量は最初の行だけ「一式」で固定し、以降は入力フォームも出さない。
- 備考は3行とも空欄で固定し、入力フォームも出さない。
- 合計は駐車場代・高速代・材料代を含めず金額を手入力する。消費税は合計の10%を自動計算して表示し、必要なら手入力で編集可能にする。合計額欄は空欄で、入力フォームも設けない。
- 吹き付けはフォームで「あり／なし」を選択し、PDFでは選択した項目に○を描画する。ありの場合だけ詳細入力欄を表示する。詳細も改行と自動折り返しに対応する。
- 丸産報告書は作業日を西暦の年・月・日で入力し、AMとPMをそれぞれ自由入力にする。作業内容は6行、作業者も6行。1行目の作業者は本人設定から一度入力したら固定する。
- 会社名は `株式会社ＴＲＣ` で固定する。

## 開発の進め方

いきなり画面を作り直さないでください。次の順で進めてください。

1. 現行AppSheetとDriveとリポジトリを調査する。
2. 現行機能の完全移行仕様書、データ項目表、帳票項目・タグ対応表、未確認事項一覧を作る。
3. 新台紙のPDFとExcelを解析し、ページサイズ、項目タイトル、印刷範囲、改行可能範囲、既存項目・新規項目を確定する。
4. 現行挙動を再現するアプリ構造を先に完成させる。データ保存、下書き・履歴、帳票ジョブ、エラー表示、バックアップ、認証・権限を分離して保守しやすくする。
5. 帳票テンプレートを差し替え可能なアダプターとして実装する。
6. タグ編集・コピー・配置・プレビュー・初期化・履歴機能を実装する。
7. 領収書処理を移行する。
8. PCとスマートフォンで、入力からPDF完成までを実際に検証する。
9. GitHub Actions、公開URL、バージョン、バックアップ、復旧手順を整える。

各段階で「今回の目標」「完了条件」「確認結果」「残課題」を短く報告してください。確認が必要なことは曖昧なまま進めず、質問をまとめて一度に聞いてください。ただし、既存資料やコードから確認できることを私に質問しないでください。

## 現リポジトリの扱い

このリポジトリには、現時点の仮アプリ、帳票背景画像、フォーム、PDFプレビュー、タグ名編集画面、タグ配置画面、ドキュメントがあります。しかし仮実装を完成版だと決めつけず、現行AppSheetとの一致を再検証してください。特に、Google Drive/Sheetsへの本番保存、認証・権限、サーバー側PDF保存、領収書画像の永続化、PDFの正確な座標合わせは本番化前に検討が必要です。

最初の作業は、現在の実装を壊さないGitチェックポイント確認と、現行AppSheetの機能棚卸しです。設計方針が変わる場合も、既存状態を削除せず、ブランチまたはタグで戻れるようにしてください。
